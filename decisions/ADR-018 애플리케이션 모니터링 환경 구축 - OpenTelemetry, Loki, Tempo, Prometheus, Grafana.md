# ADR-018: 애플리케이션 모니터링 환경 구축 - OpenTelemetry, Loki, Tempo, Prometheus, Grafana

## Status
Accepted

## Context
기존에는 콘솔과 파일 로그 중심의 단순 로깅만 수행하고 있었다.
그래서 장애 발생 시 문제의 원인과 흐름을 파악하는 데 많은 시간이 걸렸다.
그리고 트래픽 증가와 시스템이 커짐에 따라 단순 로깅만으로는 **요청 단위 추적**, **지표 기반 분석**, **이상 탐지 및 경보 설정**을 수행하기 어려워지는 문제가 있었다.

<br/>

이 문제를 해결하기 위해 아래와 같은 요구사항이 발생했다:

- 로그와 트레이스, 메트릭을 통합적으로 수집하고 상관관계 있게 분석할 수 있어야 한다.
- 장애 시 신속하게 원인을 파악할 수 있는 대시보드와 추적 시스템이 필요하다.
- 운영 서비스와 모니터링 리소스를 분리한다.

<br/>

고려한 대안:
<br/>
**1. AWS CloudWatch 사용**
    - 관리가 간편하지만 기능 제약과 비용 부담이 크고 Trace 연동이 제한적이다.
**2. 단일 서버 내 통합 구성**
    - 장애 시 전체 모니터링 스택이 영향을 받는 문제가 존재한다.
**3. OpenTelemetry + Loki + Tempo + Prometheus + Grafana 스택 구성**
    - 오픈소스를 활용해 자유로운 구성 가능
    - Trace/Log/Metrics 통합 관리 가능

## Decision

- 모니터링 전용 서버를 별도로 구축하고 다음 스택을 적용한다:
    - **OpenTelemetry Java Agent** : 코드 수정 없이 Trace 데이터 수집
    - **Promtail** : 애플리케이션 로그 수집, Loki로 전달
    - **Loki** : 로그 저장 및 조회
    - **Tempo** : 분산 추적 데이터 수집 및 조회
    - **Prometheus** : 애플리케이션 메트릭 수집
    - **Grafana** : 로그, 트레이스, 메트릭 통합 시각화
- 애플리케이션 서버와 모니터링 서버를 분리하고, Promtail을 애플리케이션 서버에 설치하여 로그를 모니터링 서버의 Loki로 전송하도록 구성했다.
- OpenTelemetry Agent를 통해 애플리케이션에서 발생하는 Trace를 Tempo로 수집하고, Prometheus를 통해 메트릭을 수집하도록 했다.
- Grafana에서 Loki, Tempo, Prometheus를 각각 Data Source로 등록해 통합 모니터링 환경을 구성했다.

<br/>

이 스택을 선택한 이유는 다음과 같다:
- **추적(Trace), 로그(Log), 메트릭(Metrics)**을 한 환경에서 통합 관리하여 장애 원인 파악과 진단 속도를 높일 수 있다.
- 모두 오픈소스 기반으로 구축되어서 비용 부담을 최소화하면서 자유롭게 커스터마이징이 가능하다.
- Grafana를 통해 대시보드를 한 곳에서 구성하여 실시간 모니터링을 구축할 수 있다.
- Promtail을 이용해 애플리케이션 로그를 Loki로 수집하고, OpenTelemetry Agent를 통해 Trace를 Tempo로 수집하여 애플리케이션 코드 수정 없이도 관측 환경을 구성할 수 있다.
- 추후에 애플리케이션 서버의 아키텍처 확장을 하더라도 같은 모니터링 스택으로 대응이 가능해 확장성이 높다.


## Consequences
**장점**
- 로그, 트레이스, 메트릭 데이터를 한 곳에서 분석할 수 있어 장애 대응 속도 향상
- Grafana 대시보드를 통해 실시간으로 시스템 상태를 모니터링 가능
- 애플리케이션 서버와 모니터링 서버 분리로 운영 안정성
- 오픈소스를 활용해 비용 절감 및 향후 확장성 확보
- Trace ↔ Log 간 상관관계 분석이 가능

<br/>

**단점 및 고려사항**
- Promtail과 Loki 간 네트워크 문제 발생 시 로그 수집 누락 가능성
- 모니터링 인프라 운영 및 관리 부담이 있다
- 초기 세팅 및 보안 그룹/포트 설정이 복잡하다
