# ADR-019: Sandbox 배포 환경 구축

## Status
Accepted

## Context
기존 CI/CD 파이프라인은 main 브랜치에 머지되는 시점에만 서버가 배포되는 구조였다. 
운영 환경만 존재했기 때문에 실제 동작하는 서버를 확인하려면 무조건 PR을 main 브랜치에 머지해야 했다.

<br/>

이로 인해 아래와 같은 문제가 있었다:
- PR이 머지되지 않으면 서버에서 기능을 확인할 수 없어, **"서버 확인 = 운영 배포"** 라는 비효율적인 흐름이 발생했다.
- 운영 배포 전 기능 검증이 어려워져 실수 가능성과 롤백 부담이 커진다.

<br/>

일반적으로 실무 환경에서는 아래와 같이 여러 환경을 운영하여 이런 문제를 해결한다:
- Sandbox : 기능 개발 중 테스트 용도의 환경
- CBT/Staging : 운영 배포 전 최종 검증 용도의 환경
- Production : 실제 사용자에게 서비스되는 운영 환경

## Decision
- main 브랜치 외의 모든 기능 브랜치에서 PR이 생성되거나 업데이트될 때, Github Actions가 자동으로 Sandbox 환경에 서버를 배포하도록 설정했다.
- Sandbox 배포는 기존 EC2 인스턴스에서 별도의 컨테이너(pointliveyoung-server-sandbox)로 운영하며, 포트(8081)를 Production과 구분한다.
- ECR 이미지는 Production과 동일한 레포지토리를 사용하되, 태그(sandbox-latest 및 short SHA)를 분리한다.
- 기존 Production 환경은 그대로 유지하여, main 브랜치에 머지될 때만 운영 서버에 배포되도록 한다.
- Sandbox 환경도 DB를 따로 운영하여 운영 환경에 영향을 주지 않도록 한다.


## Consequences

**장점**
- 기능 개발 중에도 서버에 배포하여 동작을 직접 확인할 수 있다.
- PR 머지 없이 리뷰어가 바로 Sandbox 환경에서 기능을 검증할 수 있다.
- 운영 환경에 영향을 주지 않고 테스트할 수 있다.

<br/>

**주의할 점/향후 고려사항**
- 단일 서버에서 여러 컨테이너를 운영해서 리소스 관리에 신경 써야 한다.
- Sandbox 환경이 누적될 경우 컨테이너 정리 정책이 필요하다.
- 필요 시 Sandbox 환경에도 로딩/모니터링 옵션을 부분 적용할 수 있다.
- Sandbox 환경도 별도의 EC2 인스턴스로 분리하는 방안을 추후 고려할 수 있다.
